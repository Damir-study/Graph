# Системный анализ очереди с приоритетом

## 1. Какую проблему решает структура?

Нужно выбирать следующую задачу по важности или времени выполнения, а не по времени поступления. Например, планировщику событий требуется ближайшее событие из уже известных.

Обычная FIFO-очередь не подходит, если более поздняя задача должна быть обработана раньше.

Например, задача с низкой важностью могла поступить первой, а аварийное событие — позже. Обслуживание строго по поступлению задержало бы более важную работу. Очередь с приоритетом делает выбор явным, но сама по себе не определяет, какое правило важности правильно для приложения: его задаёт пользователь системы.

## 2. Что она собой представляет?

Набор элементов с правилом сравнения приоритетов. В минимальной очереди первым выбирается минимум, в максимальной — максимум. Приоритет может быть полем записи или определяться самим значением.

```text
Добавили: A с приоритетом 5, B с приоритетом 1, C с приоритетом 3.
Если меньшее число важнее, извлечение даст: B, C, A.
```

Это абстрактный тип данных, а не обязательно куча.

Стоит различать элемент и его приоритет. Две задачи могут иметь одинаковую важность, оставаясь разными задачами с разными идентификаторами и содержимым. Сравнение только приоритетов достаточно для выбора лучшей группы, но не обязательно для определения уникальности записей.

## 3. Какие правила всегда должны выполняться?

Операция просмотра или извлечения должна выбирать элемент с наивысшим приоритетом среди находящихся в очереди. Извлечение удаляет одно вхождение и сохраняет остальные.

Правило сравнения должно быть согласованным. Если важен порядок равных приоритетов, его задают дополнительно, например номером поступления. Уникальность элементов не является обязательным свойством очереди с приоритетом.

После извлечения лучшего элемента оставшиеся должны образовывать корректную очередь для следующего выбора. Если сравнение зависит от изменяющихся внешних условий, ранее построенный порядок может устареть. Тогда нужно либо явно обновлять приоритеты, либо использовать алгоритм, который учитывает такие изменения.

## 4. Что пользователь может с ней делать?

Добавить элемент, посмотреть лучший без удаления, извлечь лучший, проверить пустоту и узнать размер. Изменение приоритета, поиск и удаление произвольной задачи — дополнительные возможности, которые поддерживаются не каждым интерфейсом.

Просмотр без удаления нужен, например, чтобы узнать время ближайшего события и решить, можно ли пока перейти к другой работе. Извлечение означает, что элемент больше не ожидает обработки в этой очереди. Проверка размера полезна для контроля нагрузки, но не говорит, сколько времени займут находящиеся внутри задачи.

## 5. Как выполняются основные операции?

На бинарной куче вставка добавляет элемент в конец и просеивает вверх. Извлечение убирает вершину, переносит последний элемент на её место и просеивает вниз.

На сбалансированном дереве задача вставляется по порядку приоритета, а извлечение находит и удаляет экстремальный узел. На неупорядоченном массиве добавление простое, но перед выбором приходится просмотреть весь набор.

Для задач A(5), B(1), C(3) просмотр возвращает B, не меняя размер. После извлечения B лучшей становится C. Если теперь добавить D(2), следующим должен быть D. Такой пример показывает, что порядок пересматривается после каждого изменения, а не вычисляется один раз при первоначальном заполнении.

## 6. Почему алгоритмы корректны?

У кучи корень имеет лучший приоритет благодаря порядку родителя относительно потомков. Просеивания сохраняют это свойство после изменений.

У дерева экстремум расположен на краю упорядоченного набора. Следовательно, разные реализации могут обеспечивать одно поведение, поддерживая разные внутренние правила. Проверять нужно и внутренние правила, и сохранность всех ожидающих задач.

Правильность очереди можно описать через набор ожидающих элементов: результат извлечения должен принадлежать этому набору и иметь лучший приоритет, а новый набор должен отличаться ровно одним извлечённым вхождением. Эта формулировка не зависит от того, используется внутри куча, дерево или массив.

## 7. Сколько ресурсов требуется?

| Основа | Добавление | Просмотр лучшего | Извлечение лучшего |
| --- | --- | --- | --- |
| Бинарная куча на динамическом массиве | `O(log n)` | `O(1)` | `O(log n)` |
| Сбалансированное дерево | `O(log n)` | `O(log n)` без сохранённого указателя на экстремум | `O(log n)` |
| Неупорядоченный массив | `O(1)` | `O(n)` | `O(n)` |

Память этих реализаций — `O(n)`. В дереве просмотр можно ускорить до `O(1)`, отдельно поддерживая указатель на экстремум. Поиск произвольной задачи в обычной куче — `O(n)`.

Выбор реализации зависит от соотношения операций. Если элементы добавляют часто, а лучший выбирают редко, неупорядоченный массив может быть приемлем. При постоянном чередовании вставок и извлечений куча даёт более равномерные затраты. Дополнительный индекс для быстрого поиска задачи увеличивает расход памяти и стоимость обновлений.

## 8. Какие случаи требуют отдельного решения?

Пустая очередь, один элемент, равные приоритеты, повтор одной задачи и изменение приоритета уже добавленного элемента. Для пустого просмотра или извлечения нужен явно заданный результат ошибки.

Две разные задачи с одним приоритетом должны различаться, если приложение должно хранить обе. При реализации через множество нельзя случайно считать их одной записью.

Изменение приоритета требует понять направление перемещения: повышение важности может поднять элемент, понижение — опустить. Для равных приоритетов стабильная очередь может сравнивать пары «приоритет, номер поступления». При этом номер должен сохранять порядок поступления в течение всего времени ожидания.

## 9. Как структура представляется в памяти?

Очередь может использовать массив кучи, связанные узлы дерева или простой массив записей. Сам контракт очереди не определяет физическое размещение.

Если требуется быстро менять приоритет конкретной задачи, часто нужен дополнительный индекс, связывающий её идентификатор с местом хранения. Это требует памяти и обновления индекса при перестановках.

При хранении в куче одна задача может многократно менять индекс во время просеивания. Поэтому сохранённый снаружи индекс нельзя считать постоянным идентификатором. Если есть таблица «идентификатор — позиция», каждую перестановку нужно отражать и в этой таблице, иначе последующее обновление затронет другую задачу.

## 10. Каковы преимущества и ограничения?

Позволяет поддерживать текущего лучшего кандидата без полной пересортировки после каждого изменения. Однако не заменяет обычную очередь, если важна очерёдность поступления.

Равные приоритеты не означают стабильный порядок автоматически. Постоянный поток важных задач может приводить к длительному ожиданию менее важных. Самовольное изменение приоритета без восстановления порядка делает результат выбора неверным.

## 11. Какие есть альтернативы?

FIFO-очередь подходит для обслуживания по поступлению. Отсортированный список или массив удобен при редких вставках. Если набор фиксирован и новых задач не будет, можно один раз отсортировать его. Для поиска записей по идентификатору нужен словарь, который решает другую задачу.

Для фиксированного набора задач сортировка один раз может быть достаточной.
