# Системный анализ словаря

## 1. Какую проблему решает структура?

Нужно находить данные по их идентификатору, не просматривая вручную каждую запись. Например, получить имя студента по номеру или значение настройки по её названию.

Словарь описывает соответствие ключей значениям, независимо от конкретного способа хранения.

Без словаря программа часто вручную проходит список записей и сравнивает их поля. При увеличении набора это становится дорого, а одинаковая логика поиска повторяется в разных местах. Словарь предоставляет общий контракт: «передай ключ — получи связанную запись», позволяя отдельно выбирать эффективный способ хранения.

## 2. Что она собой представляет?

Набор пар «ключ — значение». Ключ определяет запись, значение содержит связанные данные.

```text
Ключ: номер студента    Значение: имя
1042                   Анна
1043                   Иван
1044                   Анна
```

Ключи различаются, а значения могут повторяться. Словарь является абстрактным типом данных: деревья и хеш-таблицы — способы его реализации.

Ключ выступает именем записи внутри набора. Позиция записи в памяти не является частью этого имени и может меняться при расширении хранилища. Например, номер студента остаётся тем же, даже если запись переместилась в другой узел или ячейку.

## 3. Какие правила всегда должны выполняться?

В каждый момент одному ключу соответствует не более одной записи. Различение ключей должно быть согласованным: у дерева используется порядок, у хеш-таблицы — равенство и хеширование.

Для хеш-таблицы равные ключи обязаны иметь одинаковый хеш. Обратное неверно: одинаковый хеш может быть у разных ключей, это коллизия.

Важно заранее определить, что считать одинаковыми ключами. Если названия настроек сравниваются без учёта регистра, `Timeout` и `timeout` должны обозначать одну запись. В хеш-таблице хеширование обязано учитывать это же правило, иначе равные по смыслу ключи могут ошибочно попасть в разные области поиска.

## 4. Что пользователь может с ней делать?

Добавлять записи, получать и изменять значения по ключу, проверять наличие, удалять записи и перечислять содержимое.

Нужно определить контракт: повторная вставка заменяет значение или считается ошибкой? Получение отсутствующего ключа возвращает признак отсутствия, создаёт запись или вызывает исключение? Эти варианты нельзя смешивать без явного описания.

Операции «добавить новую запись» и «присвоить значение по ключу» могут иметь разные условия: первая запрещает повтор, вторая заменяет старое значение. Перечисление содержимого полезно для вывода и сохранения, но порядок записей нужно оговаривать отдельно. Интерфейс должен позволять отличить успешный поиск от отсутствия записи.

## 5. Как выполняются основные операции?

В словаре на дереве ключ сравнивают с ключами узлов и выбирают ветку поиска. В хеш-таблице вычисляют хеш, находят соответствующую область хранения и проверяют равенство ключей среди кандидатов.

Например, запрос по ключу 1043 возвращает «Иван». Замена имени по этому ключу меняет значение одной записи; остальные записи сохраняются. В простом массиве пар для поиска перебирают ключи последовательно.

В хеш-таблице несколько ключей могут попасть в одну корзину; тогда внутри неё проверяют подходящие записи. Другой способ — искать свободную ячейку по определённой последовательности. При удалении в таком варианте нельзя всегда просто сделать ячейку пустой: это может преждевременно оборвать путь поиска других ключей.

## 6. Почему алгоритмы корректны?

Для дерева корректность следует из правил поиска и сохранения порядка ключей. Для хеш-таблицы одинаковые ключи направляются в одну область, а окончательная проверка равенства отличает нужную запись от коллизий.

Коллизия не должна приводить к потере другой записи. Вставка, обновление и удаление должны сохранять уникальность ключей.

Например, если ключи 1042 и 1052 попали в одну корзину, сравнение ключей всё равно отличает их друг от друга. Удаление 1042 не должно удалять всю корзину вместе с записью 1052. В реализации на дереве аналогичная обязанность — сохранить остальные поддеревья после удаления узла с нужным ключом.

## 7. Сколько ресурсов требуется?

Скорость определяется реализацией.

| Основа | Поиск | Вставка | Удаление |
| --- | --- | --- | --- |
| AVL или другое сбалансированное дерево | `O(log n)` | `O(log n)` | `O(log n)` |
| Обычное BST | `O(h)` | `O(h)` | `O(h)` |
| Хеш-таблица | В среднем `O(1)` | В среднем амортизированно `O(1)` | В среднем `O(1)` |
| Неупорядоченный массив пар | `O(n)` | `O(n)` с проверкой уникальности | `O(n)` |

Оценки хеш-таблицы требуют подходящего распределения хешей и контроля заполнения. Худший случай может быть `O(n)`, отдельное расширение — тоже `O(n)`. Память обычных реализаций — `O(n)` с дополнительными расходами хранилища.

Средняя постоянная сложность хеш-таблицы не означает ровно одно действие на любой запрос. Нужно вычислить хеш и проверить кандидатов. При расширении таблицы записи распределяют заново, поэтому отдельная вставка может быть долгой. Для строк длины `L` само вычисление хеша обычно требует просмотра `L` символов, а сравнение строк также может зависеть от их длины.

## 8. Какие случаи требуют отдельного решения?

Пустой словарь, отсутствующий ключ, повторный ключ, одинаковые значения и коллизии хешей. Нужно различать «записи нет» и «значение записи пустое».

Ключ должен поддерживать сравнение или хеширование в зависимости от реализации. Его изменение после вставки может сделать запись недоступной для поиска.

Если значение может быть пустой строкой, результат «пустая строка» не доказывает отсутствие ключа: запись может существовать и содержать именно это значение. Поэтому нужен отдельный признак успешного поиска или оговорённая ошибка. При замене значения также важно определить, сохраняются ли ранее выданные ссылки на запись.

## 9. Как структура представляется в памяти?

В дереве пары хранятся в связанных узлах. В хеш-таблице используется массив ячеек или корзин; коллизии обрабатываются цепочками либо поиском другой ячейки. Эти решения дают разный расход памяти и разные требования к расширению.

Цепочки коллизий используют дополнительные связи и часто отдельные выделения памяти. У дерева больше памяти уходит на связи, зато порядок ключей выражен непосредственно в расположении узлов.

## 10. Каковы преимущества и ограничения?

Словарь связывает данные с понятными идентификаторами и скрывает способ поиска. Однако быстрый поиск по ключу не означает быстрый поиск по значению. Порядок перечисления не гарантируется самим понятием словаря и зависит от его разновидности.

Выбор ключа влияет на всё использование словаря. Если ключ — изменяемое имя человека, переименование требует аккуратного обновления записи; устойчивый числовой идентификатор обычно удобнее. Также один словарь эффективно индексирует только выбранный ключ: поиск по другому полю может потребовать перебора или дополнительного индекса.

## 11. Какие есть альтернативы?

Если нужны только уникальные ключи без значений, достаточно множества. Для маленького набора допустим простой список пар. Для нескольких значений на ключ нужен иной контракт, например словарь списков или мультисловарь.

Обычный массив позволяет получать запись по номеру ячейки без хеширования, но не подходит для произвольных разреженных идентификаторов без расхода памяти на пропуски. Упорядоченный словарь полезен для диапазонов ключей, неупорядоченный — для точного поиска. Если одному ключу должны соответствовать несколько записей, их можно хранить в коллекции как значение либо выбрать мультисловарь.
